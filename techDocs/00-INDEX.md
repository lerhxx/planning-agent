## 1. 三套文档的分工

## 5. 架构不变量（每条都有可执行判据）

```bash
# 内核零领域词（注意：shared 在仓库根，不是 src/shared）
grep -rnE "<领域词>" src/core shared | wc -l                 # → 0
# 内核不解析领域语义
grep -rn "\.code\|\.evidence\|\.suggestion" src/core | wc -l  # → 0
# 反向剥离
rm -rf src/domains/<x> && npm run build                      # → 通过（干净 worktree 里跑，用 git 还原）
# 内核零改动（M2/M3 的硬证据）
git diff --numstat m1-core-only..HEAD -- src/core shared | wc -l   # → 0
```

> ⚠️ **路径陷阱**：`shared/` 在**仓库根**，不在 `src/` 下。写成 `src/shared` 时 grep 只在 stderr 悄悄报错、仍返回 `src/core` 的结果——表面 0 通过，**实际整段 `shared/` 的检查被静默跳过**。

## 6. 维护约定

1. **代码改了，文档就得改**——尤其是 `02`（字段级）和 `03`（模块内部机制）。
2. **数字必须从代码或命令里取**，不许凭记忆写。写之前跑一遍那条命令。
3. **不确定就标注不确定**，不要含糊过去。本目录里所有"我不确定"的条目都是刻意保留的——它们比一句漂亮但错的断言有用。
4. **已知限制照实写**。面试时能讲出"这里有个洞、我为什么没填"比假装完美更可信。
