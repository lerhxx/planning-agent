## 0. 阅读约定

| 缩写 | 含义 | 在契约里的角色 |
|------|------|----------------|
| **P** (Planner) | 规划器 / Runtime，领域包 `planning` 段 + 内核调度 | 产出"要做什么"的草稿与运行态 |

## 1. 契约分层总览

`shared/` 下四类契约，各自服务不同的"写方 / 读方"：

| 文件 | 契约 | 主要写方 | 主要读方 | 回答的问题 |
|------|------|----------|----------|------------|
| `shared/plan/types.ts` | Goal / Plan / Step / StepResult / SourceRef / ClarifyQuestion / EditCommand | P + K + U | K + U | 一次任务**要做什么、做到哪了、谁能改** |
| `shared/stream/events.ts` | 9 类 SSE 事件 + JSON Patch + PlanSnapshot | K（流式 writer） | U（nodeReducer） | **实时进度**怎么增量推给前端 |
| `shared/domain/types.ts` | DomainPack 8 段（meta / tools / providers / ui / prompts / planning / evaluation / lifecycle）+ ValidationResult | D | K + U | 一个领域**能提供什么能力、怎么反幻觉** |
| `shared/run/types.ts` | RunContext / RunRequest / RunTerminalStatus | API + K | K + D | 一次 run 的**上下文与请求**长什么样 |

**为什么契约要独立成 `shared/` 而不是塞进 core？**

1. **跨端唯一真源**：`RunContext` / `EditCommand` / `Plan` 同时被服务端（core）和前端（请求体、reducer）使用。`shared/` 让两端用同一份 zod schema 校验，避免"后端改字段、前端不知道"的经典漂移。
2. **core 与领域包解耦**：core 只 import `shared/domain/types.ts` 的**接口形状**（`interface`），不依赖任何具体领域实现。领域包反过来依赖 `shared/` 定义槽位 —— 依赖方向是单向的（领域包 → shared → core 无关，core → shared）。
3. **纯数据可安全传输**：`RunContext` 刻意保持"纯数据"（不含函数），因此能被 zod 完整校验并跨端序列化。`shared/domain/types.ts` 里"可调用段"用 `interface extends z.infer<...>` 组合函数成员，但那份类型也只在 `shared` 定义一次，不存在手抄副本。
4. **领域无关性约束**：`shared/**` 强制无领域词，从编译层面保证了 core 的通用性 —— 换一个领域包，core 一行不用改。

## 2. `shared/plan/types.ts` —— 计划与步骤契约

本文件是 **Goal / Plan / Step** 的唯一真源，含状态机、溯源、错误、成本、意图、编辑溯源、澄清、编辑命令。

### 2.1 状态机枚举

**`zStepStatus`（8 态）—— Step 级状态机**

| 值 | 语义 | 终态? |
|----|------|-------|
| `pending` | 已入计划，依赖未满足或未开始 | 否 |
| `ready` | 依赖已满足，可调度 | 否 |
| `running` | 执行中 | 否 |
| `done` | 成功完成 | ✅ 终态 |
| `failed` | 执行失败 | ✅ 终态 |
| `skipped` | 被用户/编排跳过 | ✅ 终态 |
| `cancelled` | 被取消 | ✅ 终态 |
| `awaiting_user` | 等待用户决策（澄清 / 编辑） | ✅ 终态 |

> `TERMINAL_STEP_STATUSES`（源码常量）含 `done / skipped / cancelled / failed / awaiting_user`；`isTerminalStepStatus()` 是其判定函数。终态后不再参与调度。

## 3. `shared/stream/events.ts` —— 流式事件契约

AI SDK 自定义 data part 风格。**新增事件必须同步改 4 处**：本文件 / 服务端 writer / 前端 nodeReducer / 组件注册表。前端收到任何事件都要 `zStreamEvent.safeParse`，**失败即丢弃该事件（绝不白屏）**。

### 3.1 `zJsonPatchOperation` —— RFC 6902 最小子集

| 字段 | 类型 | 必填 | 默认值 | 语义 |
|------|------|------|--------|------|
| `op` | `'add'\|'replace'\|'remove'` | ● | — | 操作 |
| `path` | string(.min(1)) | ● | — | 目标路径，如 `/items/-` |
| `value` | unknown | ○ | — | 操作值 |

> **`add /items/-` = 列表追加语义**。Step 列表、组件 props 增量都走 JSON Patch，禁止整包重发 props。

### 3.2 九类事件

**① `zPlanStartEvent`** `type: 'plan_start'`

| 字段 | 类型 | 必填 | 默认值 | 语义 |

## 4. `shared/domain/types.ts` —— 领域包契约（8 段）

### 4.5 ★ `zValidationResult` —— 全文最锋利的设计

> **内核只消费 `ok` 与 `violations[].severity`**；`code / message / suggestion / evidence` 对内核不可读。这由**双重保障**强制（见下方"双重保障"），不是口头约定。

**`zViolation`**（逐字段标注可读性）：

| 字段 | 类型 | 必填 | 默认值 | 内核可读? | 语义 |
|------|------|------|--------|-----------|------|
| `severity` | `'error'\|'warning'` | ● | — | ✅ **内核可读**（据此判 error/warning） | 严重程度 |
| `code` | unknown | ○ | — | ⛔ **内核不可读** | 领域错误码（不透明） |
| `message` | unknown | ○ | — | ⛔ **内核不可读** | 领域错误消息（不透明） |
| `suggestion` | unknown | ○ | — | ⛔ **内核不可读** | 领域修复建议（不透明） |
| `evidence` | unknown | ○ | — | ⛔ **内核不可读** | 证据（不透明） |

**`zValidationResult`**：

| 字段 | 类型 | 必填 | 默认值 | 内核可读? | 语义 |
|------|------|------|--------|-----------|------|
| `ok` | boolean | ● | — | ✅ **内核可读**（校验是否通过） | 整体是否通过 |
| `violations` | Violation[] | ○ | `[]` | ✅ **仅读 severity** | 违规项（其余字段内核不可读） |

> 可调用成员：`ValidatingProvider.validate(plan, ctx): Promise<ValidationResult> | ValidationResult`。`ProviderAdapter`：`id` / `search(query, ctx)` / `detail?(id, ctx)`。

> **双重保障（本项目最锋利的设计，面试可展开）：**
> 1. **类型层**：`zViolation` 里 `code / message / suggestion / evidence` 全部是 `z.unknown()`，内核代码在 TS 类型上**根本读不出**这些字段 —— 想 switch 某个领域错误码会直接编译不过。
> 2. **运行层**：内核确实**有运行时消费点**，且只读 `ok` + `severity`。在 `src/core/run/engine.ts`：
>    - `validateCurrent`（`engine.ts:330-335`）调用 `validatePlan` 后只取 `{ ok: result.ok, severity: highestSeverity(result) }`——`highestSeverity`（`src/core/planning/validate.ts:55-57`）只扫 `violation.severity`，从不碰其他字段；
>    - 计划生成后（`engine.ts:505-509`）、重排候选后（`engine.ts:429-432`）、逐步校验（`engine.ts:522-523`）三处都把 `{ ok, severity }` 交给 `decideValidationAction`，**从不读 `.code` / `.message` / `.suggestion` / `.evidence`**（`engine.ts:328` 注释：红线 8）。
>
> 设计意图：内核只关心"通不通过 + 严重级别"，领域可自由返回丰富诊断信息给前端，而内核在**类型 + 运行**两层都被锁死无法依赖领域语义 —— 比单说"类型上无法读取"更扎实。

## 6. zod 使用约定（本项目的红线）

### 6.1 `z.infer` vs `z.input` —— 真实存在的坑

- **`z.infer<T>`** = 输出类型（经过 `.default()` / transform 之后）。字段若带 `.default()`，在 `z.infer` 里变成**必填**（因为默认值已填好）。
- **`z.input<T>`** = 入参类型（transform 之前）。带 `.default()` 的字段在 `z.input` 里是**可选**的。
- **本项目真问题**：`src/core/degrade/policy.ts` 用 `z.input` 定义 `DegradeInput`：

  ```ts
  export const zDegradeInput = z.object({
    componentKnown: z.boolean().default(true),
    parseOk: z.boolean().default(true),
    /* ... 全部字段都带 .default() */
  });
  // ★ 用 z.input 而不是 z.infer：
  export type DegradeInput = z.input<typeof zDegradeInput>;
  ```

  若改用 `z.infer`，调用方会被强制要求补齐所有默认值字段 —— **默认值形同虚设**（调用方不传也不行，等于手写默认值被架空）。所以：**对外接收"可能省略默认值"的输入用 `z.input`，对外输出"已填好默认值"的结果用 `z.infer`**。

### 6.2 `.default()` 的纪律

所有"运行态由内核补齐 / 可选但有合理默认"的字段一律 `.default(...)`（如 `Step.status` 默认 `pending`、`RunContext.budgetRemainingCNY` 默认 `2`）。这样：
- schema 自动填充默认值；
- 配合 `safeParse` 得到"已归一化"的对象，无需调用方兜底。

### 6.3 `safeParse` 失败降级

- 内核 / 前端消费一切外部数据（模型输出、网络 JSON、SSE 事件）前必须 `schema.safeParse`，失败走降级（流式事件失败即丢弃该事件、不白屏；props 校验失败→rawPayload 降级）。
- 禁止 `schema.parse` 直接抛错污染主流程。

### 6.4 为什么禁止手写两份类型

- 类型唯一真源 = `shared/**` 的 zod schema。同构的 TS 接口（如 `DomainPack`）也**只在 `shared` 定义一次**（`interface extends z.infer<...>`），通过 `import type` 复用。
- 手写副本必然与 schema 漂移，且 `.default()` 的"可选/必填"差异（`z.input` vs `z.infer`）极易写错 —— 这是本项目已经踩过并固定下来的坑。

### 7.4 `ValidationResult`（内核只读 ok + severity）

```json
{
  "ok": false,
  "violations": [
    { "severity": "error", "code": "BUDGET_EXCEED", "message": "超预算", "suggestion": "减少 1 天", "evidence": { "gap": 500 } },
    { "severity": "warning", "code": "TIGHT_SCHEDULE", "message": "行程过紧" }
  ]
}
```

> 内核**只消费 `ok` 与 `violations[].severity`**（双重保障见 §4.5）：`ok=false` 且有 `error` 级 violation → 阻断；`warning` 不阻断。`code/message/suggestion/evidence` 在类型层是 `z.unknown()`、运行层又不被读取，仅供前端展示。
