## 1. 测试哲学：测试是**架构约束的执行手段**

大多数项目里测试的作用是"防 bug"。本项目不是——至少不主要是。

本项目有一条元规则（`CLAUDE.md` 绝对红线、`docs/CONSTRAINTS.md` 第一部分 §3）：

> **能自动验证的约束才是真约束。写不出判据的约束，等于没写。**

| 抽象要求 | ❌ 坏写法 | ✅ 好写法（本项目采用） |
|---|---|---|
| 内核要通用 | "内核不要耦合业务" | `grep -rnE "<领域词>" src/core shared \| wc -l` 必须为 0 |
| 领域可插拔 | "删掉领域应该没事" | `rm -rf src/domains/<x> && npm run build` 必须通过 |
| 可扩展 | "加新领域内核不用改" | `git diff --numstat <core-tag>..HEAD -- src/core/** shared` 必须为 0 |

于是测试在本项目承担三类职责，缺一不可：

| 职责 | 防的是什么 | 例子 |
|---|---|---|
| **防回归** | 改坏已有行为 | `planCompiler.test.ts` 断言 `batches` / `edges` 精确相等 |
| **承红线** | 架构红线被悄悄穿透 | `edgeCases.test.ts` 四条拦截路径必须**可达且可证伪** |
| **证伪架构主张** | "通用 / 可扩展"沦为口号 | 第 6 节的 5 条自动化验证 |

> **一条必须内化的区分：测试通过 ≠ 功能接通。**
> 一个函数可以被 20 个用例证明"参数算对了"，同时在整个系统里**从来没有被调用过**——本项目真的发生过（见 4.4）。因此端到端层的断言目标不是返回值，而是 **"这段代码真的被执行了"**（用 spy 计数）。

## 2. 测试分层

| 层 | 测什么 | 放在哪 | 代表文件 | 用例数 |
|---|---|---|---|---|
| **L1 纯函数单测** | 单个纯函数的输入→输出、边界值、不可变性 | 与被测文件**同目录** `<module>.test.ts` | `cycleDetect` / `planCompiler` / `gates` / `impact` / `edit` / `policy` / `scheduler` / `parse` / `domainRegistry` / `nodeReducer` | **96** |
| **L2 端到端引擎测试** | `runGoal()` 全流程：事件流顺序、终态、兜底组件、领域 Provider 是否真的被调用 | **`src/test/`**（统一目录） | `closedLoop` / `edgeCases` / `validation` | **33** |
| **L3 架构不变量** | 领域词、内核禁读领域语义、反向剥离、M3 内核零改动 | CI shell（**不是 vitest**） | — | — |

**为什么 L2 单独放 `src/test/`、而不是挨着被测文件？**

因为端到端测试必须 `import { registerAllDomains } from '@/src/domains'`——一旦放在 `src/core/` 下，内核目录里就出现了领域 import 路径，**第 1 条架构不变量当场破裂**。`closedLoop.test.ts` 的文件头注释把这条写死了：*"内核目录必须保持零领域词，连 import 路径里都不允许出现领域名。"*

**一条硬要求**：每个新模块必须带单测；**纯函数必须有单测**（`CONSTRAINTS.md` L3）。这不是倡议，是红线 15 的反面。

## 4. ★ 踩过的坑（本篇最有价值的部分）

以下问题全部由 M1 验收时的**独立 QA** 抓出，均已修复，且**每一条都在测试里留下了防回潮的断言**。

### 4.1 收敛判定在数学上不可能触发

| | |
|---|---|
| **症状** | `NO_CONVERGENCE` 这条例行公事般写进 PRD 的兜底规则，**在真实闭环里永远不会被触发**——它是一段"看起来在工作"的死逻辑。 |
| **根因** | `stepSignature` 里含 `id`，而重排**强制生成新 id**（`r2-` 前缀）。于是新旧计划的签名集合**必然不相交** → Jaccard = 0 → `delta = 1` → `isStagnant(1) === false`。无论模型多"原地打转"，判定结果恒为"已收敛"。 |
| **反向误伤** | 修 A 面露 B 面：若改成按**整个计划**比较，25 步的计划只重排其中 1 步 → `delta = 1 − 24/26 ≈ 0.077 < 0.15` → 一次**正常的局部重排**被误判成"原地打转"，直接强制转人工。（该数值即 `gates.test.ts` 第 104 行的 `expect(wholeDelta).toBeCloseTo(1 - 24 / 26, 5)`。） |
| **修法** | 两处同时改：① `stepSignature` 摘掉 `id`，退化为 `` `${step.type}|${normalizeTitle(step.title)}` ``（`shared/plan/types.ts:335`）；② 新增 `subtreeDelta()`（`gates.ts:99`），**比较域从"整个计划"收窄到"受影响子树"**（被替换的那几步 vs 本次新生成的那几步），闭环改调它。`planDelta()` 保留，但注释明确写"供测试与诊断用"。 |
| **防回潮** | 把旧 bug 写成**反例断言**永久留在测试里：`gates.test.ts` 第 102 行 `★ 反例：若按整个计划比，delta < 0.15 会被误判成原地打转（旧 bug）`；`edgeCases.test.ts` 第 91 行 `★ 25 步计划只重排 1 步 → 不得判 NO_CONVERGENCE`。 |

**教训**：`gates.test.ts` 原本有 20 个用例**全绿**，但它们测的是"闸门参数正确"（`maxReplans === 5`、`minDelta === 0.15`），**不是"闸门能拦住它该拦的东西"**。
> **参数正确 ≠ 行为正确。** 一条拦截规则必须有"它真的拦下了什么"的用例，也必须有"它不会误伤什么"的反例。

### 4.2 填充断言（凑数）

| | |
|---|---|
| **症状** | `closedLoop.test.ts` 里曾有 `beforeAll(() => expect(true).toBe(true))`——一个永远为真、不触碰任何产品代码的"用例"。 |
| **根因** | 追求"用例数"这个数字指标，而不是追求覆盖。**用例数是结果，不是目标。** |
| **修法** | 删除。当前版本无 `beforeAll`。 |
| **防回潮** | 按第 5.4 节自检清单第 6 条过一遍；review 时看到 `expect(true)` / 空 `beforeAll` / `expect(x).toBeDefined()` 直接打回。 |

### 4.3 脆弱断言（依赖调度顺序）

| | |
|---|---|
| **症状** | 原有一条断言硬编码 `s-2` 为 `done`。并行批次里"谁先失败"取决于 `Promise.all` 的内部调度顺序 → 用例间歇性红（**flaky**）。 |
| **根因** | 断言写的是**实现细节**（某个具体 id 的终态），而不是**不变量**（"重排前已完成的步骤，重排后应当原样保留"）。 |
| **修法** | 改成从**事件流推导**：新增 `doneBeforeReplan(events)`，扫到 `plan_status === 'replanning'` 之前所有 `step_status === 'done'` 的 id 集合，再遍历断言这些 id 在最终计划里仍存在且仍为 `done`。**与执行顺序无关。** |
| **防回潮** | 该函数上方的注释本身就是规范：*"不用硬编码某个 id：并行批次里谁先失败取决于 Promise 的调度顺序，断言必须与顺序无关，否则测试会变成 flaky。"* |

### 4.4 死代码：`validatePlan()` / `highestSeverity()` 零调用零测试

| | |
|---|---|
| **症状** | 这两个函数写完了、类型也对、也"跑得通"，但**零调用、零测试**。后果是 PRD 主路径（**校验型 Provider**）在闭环里**根本没接上**——校验链路断在半路，谁也没发现。 |
| **根因** | 单测只覆盖了 `validateStep`（逐步骤），没覆盖 `validatePlan`（聚合）；而**没有任何测试断言"闭环真的调用了它"**。 |
| **修法** | ① 补 `src/test/validation.test.ts`（15 个用例）覆盖聚合语义与 `highestSeverity`；② 在 `edgeCases.test.ts` 第 232 行加 **spy 计数**：替换 `pack.providers.createValidator`，跑完一轮闭环后断言 `calls >= 1`，`finally` 里还原。 |
| **防回潮** | `edgeCases.test.ts` 用例名即契约：`★ 跑一轮闭环 → 领域的 createValidator 至少被调用一次`。 |

**教训（最重要的那句）**：
> **测试通过 ≠ 功能接通。**
> 验证"接上了"要断言**执行证据**（调用计数 / 副作用 / 事件流里出现过），而不是只断言返回值。

### 4.5 循环内断言缺 `expect.assertions(n)`

| | |
|---|---|
| **症状** | `for (const step of factSteps) { expect(step.result.sourceRefs.length).toBeGreaterThan(0) }`——当 `intent` 为 `null` 时 `factSteps` 为空数组，循环 0 次、**0 个断言**，用例**静默通过**。测试在撒谎。 |
| **根因** | Vitest 不强制最小断言数；空集合上的循环断言是最常见的假通过模式。 |
| **修法** | 循环**之前**先断言集合非空，再声明总断言数：`expect(factSteps.length).toBeGreaterThan(0);` + `expect.assertions(1 + factSteps.length);`（`closedLoop.test.ts:197-198`）。 |
| **防回潮** | 全仓 `expect.assertions` 目前**只有这一处**（`grep -rn "expect.assertions" src/`）。写循环断言时默认加上。 |

## 5. 怎么写新测试

### 5.1 命名与放置约定

| 场景 | 位置 | 命名 |
|---|---|---|
| 内核纯函数 | 与被测文件同目录：`src/core/<module>/<name>.test.ts` | 同模块名 |
| 前端纯逻辑（reducer / patch） | 与被测文件同目录：`src/features/.../<name>.test.ts` | 同模块名 |
| 需要 import 领域包的端到端 | **`src/test/<scenario>.test.ts`**（统一目录，不得放 `src/core/`） | 按场景命名 |
| 夹具 | `src/test/fixtures.ts` 的 `makeStep` / `makePlan` / `makeChain` | — |

**夹具纪律**：`makeStep` / `makePlan` 从 **zod schema 出发**（`zStep.parse({...defaults, ...partial})`），**禁止手写第二份类型**——schema 一变夹具跟着变，不会出现"测试用的是旧结构"。

**用例命名**：`describe` 用模块名，**用例名写"场景 → 预期结果"**；修复过的 bug 一律加 `★` 前缀并在注释里写清"旧 bug 是什么"，让后人知道这条断言为什么存在。

### 5.2 模板 A · 纯函数测试

```ts
import { describe, expect, it } from 'vitest';
import { makePlan, makeStep } from '@/src/test/fixtures';
import { collectImpact } from './impact';

describe('collectImpact', () => {
  it('传递闭包：只收直接依赖不算够', () => {
    // Arrange —— 夹具从 zod 出发，不手写第二份类型
    const plan = makePlan([
      makeStep({ id: 'a', order: 0 }),
      makeStep({ id: 'b', order: 1, dependsOn: ['a'] }),
      makeStep({ id: 'c', order: 2, dependsOn: ['b'] }),
      makeStep({ id: 'd', order: 3, dependsOn: ['c'] }),
    ]);

    // Act
    const impact = collectImpact(plan, ['a']);

    // Assert —— 断言"它做了什么"，不是"它没崩"
    expect(impact.impactedIds).toEqual(['a', 'b', 'c', 'd']);
  });
});
```

### 5.3 模板 B · 端到端引擎测试

```ts
/**
 * 放在 src/test/ 而不是 src/core/：本文件要 import 领域包，
 * 内核目录必须保持"零领域词"（连 import 路径里都不允许出现领域名）。
 */
import { describe, expect, it } from 'vitest';
import type { StreamEvent } from '@/shared/stream/events';
import { runGoal, type EngineInput } from '@/src/core/run/engine';
import { createMockRuntime } from '@/src/core/runtime/mock';

async function run(simulate: EngineInput['simulate']) {
  const events: StreamEvent[] = [];
  const result = await runGoal(
    { goal: '两路采集后汇总成一版结论，预算不超过 500 元，三天内完成', simulate },
    {
      runtime: createMockRuntime({ latencyMs: 0 }), // 每个 run 独立实例，故障注入状态互不泄漏
      emit: (e) => events.push(e),
      sleep: async () => undefined,                 // 不真睡
      streamDelayMs: 0,
      now: () => new Date('2026-01-01T00:00:00.000Z'), // 固定时钟，杜绝时间 flaky
    },
  );
  return { result, events };
}

describe('XXX 拦截路径', () => {
  it('注入不可恢复失败 → 终态 YYY，且下发 ErrorState（不白屏）', async () => {
    const { result, events } = await run('fatal');

    expect(result.status).toBe('failed');
    expect(result.reason).toBe('YYY');
    expect(nodeComponents(events)).toContain('ErrorState');
    expect(events.filter((e) => e.type === 'done')).toHaveLength(1); // 必须有终态事件
  });
});
```

**端到端三条硬要求**：
1. **零网络、零 API Key** —— 全程 `createMockRuntime`。
2. **注入全部不确定源** —— `now()` / `sleep()` / `latencyMs` / 故障脚本；同一份输入必须永远得到同一条事件流。
3. **断言"接通"而非"返回"** —— 需要证明某段领域代码被执行时，用 spy 计数（见 4.4）。

### 5.4 断言强度自检清单（写完逐条过）

| # | 自检 | 不通过的样子 |
|---|---|---|
| 1 | 失败路径有断言吗？ | 只测了 happy path |
| 2 | 断言的是**输出值**还是"没抛错"？ | `expect(fn()).toBeDefined()` / 只有 `not.toThrow()` |
| 3 | 循环里的断言有 `expect.assertions(n)` 吗？ | 空集合 → 0 断言 → 假通过（见 4.5） |
| 4 | 断言**依赖执行顺序**吗？ | 硬编码并行批次里某个具体 id 的终态（见 4.3） |
| 5 | 浮点比较用 `toBeCloseTo` 吗？ | Jaccard / 比例用 `toBe` |
| 6 | 有没有**填充断言**？ | `expect(true).toBe(true)`、空 `beforeAll`（见 4.2） |
| 7 | **这条测试能被一个错误实现骗过吗？** | 把被测函数临时改成 `return null` / `return []`，测试竟然还绿 |
| 8 | 纯函数测了**不可变性**吗？ | 缺"入参 JSON 快照前后一致"的用例 |

> 第 7 条是最狠的一条：**改坏实现，测试必须变红**。变红不了，说明这条测试没有在守护任何东西。

## 6. 架构不变量的自动化验证

这些**不在 vitest 里跑**（它们验证的是目录与 git，不是运行时行为），但它们是本项目真正的"架构门禁"。

| # | 不变量 | 命令 | 期望输出 |
|---|---|---|---|
| 1 | 内核零领域词 | `grep -rnE "demo" src/core shared \| wc -l` | **`0`**（本机实测 `0`） |
| 2 | 内核不读领域语义 | `grep -rn "\.code\|\.evidence\|\.suggestion" src/core \| wc -l` | **`0`**（本机实测 `0`） |
| 3 | 内核不 import 领域 | `grep -rn "domains" src/core shared \| wc -l` | **`0`**（本机实测 `0`） |
| 4 | 领域可剥离 | `rm -rf src/domains/demo && npm run build` | **通过** |
| 5 | 新增领域后内核零改动 | `git diff --numstat m1-core-only..HEAD -- 'src/core/**' shared \| wc -l` | **`0`**（本机实测 `0`） |

**执行细节与坑**：

- **#1 的 `<领域词>` 要替换成具体领域名**。当前仓库只有 `demo` 一个领域包（`src/domains/` 下为 `demo/ index.ts ui.ts`），新增领域时必须**逐领域跑一遍**。另外**全仓文档曾普遍把契约目录误写成 `src/shared`**，本仓库实际路径是根目录的 `shared/`（无 `src/` 前缀）——该笔误已在 README / `docs/` 三份 / `techDocs/` 全部修正，写命令以**实际路径**为准。这个笔误危险在于：`grep ... src/core src/shared` 遇到不存在的路径只往 stderr 报错、仍返回 `src/core` 的结果，表面 `0` 通过，**实际整段 `shared/` 的检查被静默跳过**。
- **#4 会真的删除目录**，只能在干净工作区或临时 worktree 里跑，跑完用 `git checkout -- src/domains` 还原；**不要在有未提交改动的工作区执行**（`npm run build` 本身已由主理人独立验证通过：`/` 静态 + `/api/run` 动态）。
- **#5 现在恒为 0**，因为 `HEAD == m1-core-only`。它的真正价值在 **M3 新增领域之后**：加完领域再跑一次，输出必须是 `0`——这就是"内核可扩展"这条主张的**可自动验证证据**。

> 这 5 条就是 `CONSTRAINTS.md` 说的"**判据**"。第 1、2、3 条把"内核要通用"变成了 `wc -l`；第 4 条把"领域可插拔"变成了一次 build；第 5 条把"可扩展"变成了一个 git diff。**没有判据的架构主张，只是愿望。**

## 7. CI 门禁建议

### 7.1 建议顺序

```bash
# ── Stage 1 · 架构门禁（毫秒级）─────────────────────────────
grep -rnE "demo" src/core shared | wc -l                            # 必须 0
grep -rn "\.code\|\.evidence\|\.suggestion" src/core | wc -l        # 必须 0
grep -rn "domains" src/core shared | wc -l                          # 必须 0
git diff --numstat m1-core-only..HEAD -- 'src/core/**' shared | wc -l  # 新增领域后必须 0

# ── Stage 2 · 契约真源 ─────────────────────────────────────
npm run typecheck

# ── Stage 3 · 风格 ─────────────────────────────────────────
npm run lint

# ── Stage 4 · 行为 ─────────────────────────────────────────
npm test

# ── Stage 5 · 可构建 ───────────────────────────────────────
npm run build
```

### 7.2 为什么是这个顺序

| Stage | 理由 |
|---|---|
| **1 架构 grep 放最前** | 毫秒级、零依赖，且**失败时后续所有结果都不可信**——架构都破了，"测试全绿"毫无意义。fail fast，且失败信息醒目、独立于编译噪音。 |
| **2 typecheck** | 类型唯一真源是 zod schema（`z.infer`），**契约漂移在这里最先、最精确地暴露**。放在测试之前，避免在已经类型错误的代码上白跑 86 秒。 |
| **3 lint** | 秒级，挡住"测试能过但代码在腐坏"的问题（未使用变量、显式 `any`、react-hooks 规则）。比测试便宜得多，先跑。 |
| **4 test** | 最贵（86s）但验证的是**行为**。放第四位是因为前面三道门能在几秒内拦掉大多数低级错误。 |
| **5 build** | 最慢最贵，且**能抓住单测覆盖不到的东西**：`app/` 与 React 组件的实际引用错误、Server/Client 边界错误。只有前面全绿才值得付这个钱。 |

**与 `CLAUDE.md` 现状的区别**：现状是 `npm run typecheck && npm run lint && npm test` 一条串，三条 grep 放在**最后**。建议改成 **grep 先行**——架构门禁失败时，测试结果已经没有意义了。另外 `npm run build` 在 `CLAUDE.md` 里只用于"反向剥离"验证、不进日常串；CI 有机器时间，补进 Stage 5 能白捡一层保护（它能抓住 `app/` 与 React 组件里单测覆盖不到的引用错误）。

**一条 CI 专属建议**：`npm test` 的 86 秒里只有 185ms 是真正的用例执行。CI 上开 `--changed`（配合 `--changedSince=main`）或调整 `isolate`，可以把 PR 阶段的反馈压到秒级；**全量跑留给 main 分支**。

## 8. 覆盖率现状与缺口（诚实版）

`node_modules/@vitest` 下**没有 coverage 包**，`package.json` **没有 coverage script**——
> **本项目当前没有行覆盖率数字。** 下面给的是**基于测试文件分布的定性判断**，不是仪器测出来的百分比。任何声称"覆盖率 XX%"的说法都是编的。

**已覆盖**：`src/core/**` 全部纯函数模块（compiler / planning / replan / degrade / execution / registry / goal）、`src/features/run/nodeReducer`、引擎端到端三条主线（正常闭环 / 拦截路径 / 校验链路）。
