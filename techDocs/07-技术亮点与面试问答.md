## 0. 电梯陈述（直接背）

### 30 秒版

> 我做了一个**目标驱动的规划型 Agent 基座**：用户只给一句话目标，系统产出一份**可见、可编辑、可中断的计划**，然后逐步执行、遇到失败只重排受影响的部分。核心主张是**内核领域无关**——所有领域语义收敛在 Domain Pack 里，内核只认 `ok` 和 `severity` 两个信号。M1 用 MockRuntime 连模型一起 mock，**零 API Key 跑通了"目标→计划→执行→重规划"闭环**，并靠 `git diff` 证明"新增领域不改内核一行"。

### 2 分钟版（按这个顺序展开）

1. **为什么做**：现有 Agent（ReAct / 单步 tool-call）把计划藏在大模型内部，用户既看不见也改不了，失败就黑盒重来。我把"计划文档"提升为一等公民——它是可序列化的数据，用户能编辑、系统能 diff、失败能局部回滚。
2. **内核怎么保持干净**：`src/core/**` 与 `shared/**` 零领域词；内核消费校验结果时只读 `ok` + `violations[].severity`，绝不读 `.code/.message/.suggestion/.evidence`。这让我能用一条 grep 命令证明架构没破。
3. **动态重规划怎么做**：失败时反向收集下游**受影响子树**，只重排那几步；已完成步骤 id 不变 = 天然幂等键。配三重闸门（次数 ≤5 / 成本 ≤¥2 / 时长 ≤25s）和收敛判定（子树 Jaccard delta < 0.15 判原地打转，强转人工），**不会无限循环**。
4. **反幻觉**：事实数据（价格/评分/数值）只能来自 Provider，模型产出的一律丢弃；`producesFacts` 的步骤结果若无 `SourceRef` 直接判失败。
5. **工程纪律**：类型唯一真源是 zod schema；流式用 SSE + JSON Patch `/items/-` 增量、前端 16ms 合批；三级降级 `RawPayloadCard → ClarifyOptions → ErrorState` 保证**绝不白屏**。
6. **可验证**：M1 通过 typecheck 0 / lint 0 / 129 测试全绿 / `next build` 通过；新增领域改内核文件数 = 0（git diff 硬证据）。

## 1. 可讲的技术亮点（★）

每条按 **问题 / 方案 / 为什么这么选 / 代价或替代 / 一句话怎么讲** 组织。

### 1.1 计划文档作为一等公民（而非 LLM 内部循环）

- **问题**：ReAct 式 Agent 把"下一步做什么"压在模型上下文里，用户无法审阅、无法干预、失败无痕。
- **方案**：Plan 是结构化数据对象（`Plan`/`Step` 的 zod schema），经 `PlanCompiler` 编译成执行图（IR）再跑；用户编辑走 L0/L1/L2 三档回写。
- **为什么这么选**：让"计划"成为用户与系统之间的**契约层**，可控、可中断、可审计。
- **代价**：多一层编译与编辑回写逻辑；但换来了可编辑性这个核心卖点。
- **一句话怎么讲**："我把 Agent 的'思考过程'外化成了一份可序列化、可 diff、可编辑的计划文档，模型不是黑盒循环，而是计划的生成器与执行器。"

### 1.2 内核不认识领域语义（只消费 `ok` + `severity`）

- **问题**：内核一旦 switch 领域错误码，就把领域耦合死，加领域必改内核。
- **方案**：`ValidatingProvider.validate()` 返回 `{ ok, violations: [{ severity, code, message, ... }] }`；内核只看 `!ok` 与最高 `severity`，触发码统一用内核通用码 `PROVIDER_VALIDATION_FAILED`。
- **为什么这么选**：领域差异被封死在 Domain Pack 内，内核成为纯调度器。
- **代价**：领域想表达"预算超支"这种细粒度原因时，内核不会据此分支——但细粒度原因本来就该由领域自己的 UI 去呈现。
- **一句话怎么讲**："内核是个'哑'调度器：它只问校验'过没过、严重不严重'，至于为什么没过，那是领域包的事，内核一概不读。"

### 1.3 收敛判定按"受影响子树"比较（踩过两个方向的 bug）

- **问题**：怎么判断重规划"有没有在改东西"，避免原地打转无限重排？
- **方案**：`subtreeDelta` = `1 - Jaccard(被替换步骤集合, 新生成步骤集合)`，阈值 0.15；delta 过小 → `NO_CONVERGENCE` 强转人工。
- **踩过的 bug（两个方向并存，且都固化成了 `gates.test.ts` 的反例断言，最有说服力）**：根因是同一刀——**比较域错（比了整个计划）+ `stepSignature` 含 `id`**。
  - **方向 (a)：delta 恒为 1.0 → "原地打转"永远触发不了**。重排后步骤 id 必变（如 `s-1` → `r2-0`），旧签名把 `id` 算进去，于是相同内容被判成两个不同 step → Jaccard = 0 → **delta = 1.0** → 系统认为"变化巨大"，收敛判定**数学上不可能**判出原地打转。修复后签名去掉 `id`（`gates.test.ts:88-93` 的反证：同 type+同 title → delta 0）。
  - **方向 (b)：delta 过小 → 正常重排被误杀**。25 步计划只重排 1 步，按整个计划比 delta = `1 - 24/26 ≈ 0.0769 < 0.15` → 被误判成原地打转、错误地中止修复。修复后比较域收窄到**受影响子树**（`gates.test.ts:102-109` 把此写成反例断言防回潮）。
- **为什么这么选**：比较域选错会让收敛闸门要么"永不触发"（a）、要么"误杀正常修复"（b），两个方向都失控。
- **一句话怎么讲**："收敛判定我踩过两个方向的坑：签名含 id 会让 delta 永远 1.0、判定根本触发不了；比整个计划又会让只动一步被误判原地打转。两刀同根——签名去 id + 比较域收窄到受影响子树，现在都用测试钉死了。"

### 1.4 已完成步骤 id 不变 = 天然幂等键

- **问题**：重规划后若步骤 id 变了，已渲染的结果节点会失效、已做的活要重做。
- **方案**：`impact.ts` 的 `collectImpact` 反向收集下游时**剔除 `done` 步骤**；`applyReplanDraft` 只替换受影响部分，保留 `done` 的 id 与状态。
- **为什么这么选**：id 稳定 → 幂等键稳定 → 重试/续跑安全，前端节点不用重建。
- **代价**：重排后的新步骤要用带 revision 前缀的新 id（如 `r2-0`），不能复用旧 id。
- **一句话怎么讲**："重规划是'局部子树重建'，已完成的那几步连 id 都不变，所以已经是幂等键，既不用重跑也不丢结果。"

### 1.5 PlanCompiler 纯函数 + 环检测

- **问题**：依赖图可能成环、可能有悬空依赖，编译必须可单测、可终止。
- **方案**：`compilePlan` 纯函数：`PLAN_DEPENDENCY_MISSING` → `PLAN_CYCLE_DETECTED`（Kahn 拓扑 + DFS 取具体环路径）→ `PLAN_PARALLEL_GROUP_DEPENDENCY` → 算拓扑批次。无环才出 IR。
- **为什么这么选**：纯函数无副作用，Mock 和真 Runtime 都能复用，改框架不用重写。
- **代价**：必须放在 `src/core/compiler/`，**禁止放进 runtime 目录**（否则换框架要重写）。
- **一句话怎么讲**："编译是纯函数，输入 Plan 输出执行图，环检测保证要么报错要么必然终止，不靠运行时碰运气。"

### 1.6 三级降级不白屏

- **问题**：模型/网络返回脏数据，UI 最容易直接崩或白屏。
- **方案**：`degrade/policy.ts` 的 `decideDegrade` 按优先级落 `RawPayloadCard → ClarifyOptions → ErrorState`（等待期还有 `SkeletonList`）。每个失败分支都落到四兜底之一。
- **为什么这么选**：降级链与传输层解耦，集中在 `ComponentRenderer`，任何组件都能套用。
- **代价**：多写一层 props 完整性判定（`isPropsComplete`），但换来了"绝不白屏"的硬保证。
- **一句话怎么讲**："所有模型输出先 safeParse，失败不是崩，是先展示原始载荷、再让用户点选、最后给错误态——三级兜底，绝不白屏。"

### 1.7 流式用 JSON Patch 增量 + 16ms 合批（禁 `ai/rsc` 的理由）

- **问题**：组件 props 整包重发既浪费也闪；`ai/rsc` 的 `streamUI` 官方标 experimental，且把渲染下沉到服务端 RSC，丢掉了我"计划客户端可编辑"的自主权。
- **方案**：SSE 下发 `component_props_delta`（`{"op":"add","path":"/items/-","value":{...}}`），`nodeReducer` 用 RFC 6902 增量累积；`useCoalescedNodes` 默认 16ms 合批，避免每个 patch 触发一次 React 重渲染。
- **为什么这么选**：增量 = 流式体验顺滑 + 带宽省；16ms 合批把高频 patch 压成每帧一次 setState。
- **代价**：前端要维护一个 JSON Patch 应用器（已单测 `applyPatch`）；但相比 `streamUI` 把组件绑死在服务端，这个方案保留了客户端完整控制权。
- **一句话怎么讲**："我用 SSE + JSON Patch 做流式增量，前端 16ms 合批，而不是用 experimental 的 `ai/rsc`——因为我的计划要在客户端可编辑，不能把渲染交给服务端 RSC 托管。"

### 1.8 反幻觉：事实只能来自 Provider

- **问题**：LLM 会自信地编价格、评分、工时。
- **方案**：`Observer.observe` 对 `intent.producesFacts === true` 的步骤，结果若无 `sourceRefs` 一律判失败（触发码 `SOURCE_MISSING`）；事实字段在模型侧直接丢弃，只用 Provider 返回值。
- **为什么这么选**：把"事实可信"的责任从模型移到数据源，内核用一道硬闸门兜底。
- **代价**：mock 数据必须标 `isEstimate` 并显示免责声明——这反而成了诚实性的展示点。
- **一句话怎么讲**："凡是带数字的事实，必须带 SourceRef 溯源；模型产出的事实字段我直接扔掉，没来源的就判失败，不让它混进结果。"

### 1.9 双 Runtime（Mock 先行）作为"框架可替换"的证据

- **问题**：怎么证明内核真的不依赖某个具体执行框架？
- **方案**：内核只依赖 `RuntimeAdapter` 接口；M1 先实现 `MockRuntime`（连模型也脚本化，零网络零 API Key），`MastraRuntime` 后续按同一接口接入、内核零改。
- **为什么这么选**：Mock 先行 = 立刻能跑闭环 + 能做故障注入（retryable/fatal/clarify），且天然证明内核与框架解耦。
- **代价**：要写一套脚本化 fixture；但这是"可替换性"最硬的证据。
- **一句话怎么讲**："我先把内核跑在 MockRuntime 上，连模型都是脚本，这样零 Key 就能演示闭环，也顺手证明：内核只认 RuntimeAdapter 接口，换 Mastra 内核一行不用动。"

### 1.10 领域词 grep = 0 作为可自动验证的架构约束

- **问题**："内核领域无关"这种话人人会说，怎么证明？
- **方案**：把约束写成可执行判据——`grep -rnE "<领域词>" src/core shared | wc -l` 必须为 0；`grep -rn "\.code\|\.evidence\|\.suggestion" src/core` 必须为 0；`rm -rf src/domains/<x> && npm run build` 必须通过；`git diff --numstat m1-core-only..HEAD -- src/core shared | wc -l` 必须为 0。
- **为什么这么选**：能自动验证的约束才是真约束，写不出判据的约束等于没写。
- **代价**：每次改动都要跑这组命令；但这是"可扩展"主张唯一的硬证据。
- **一句话怎么讲**："我说内核领域无关，不是嘴上说的——这条 grep 命令输出恒为 0，而且删掉任何领域包 build 照样过、git diff 内核改动数为 0，这就是证据。"

## 2. Mastra 问答（★★ 最容易被问倒，口径一字不差）

> 三句**绝对不能说**（都会被当场拆穿）：
> ❌ 「Mastra 是静态 DAG」
> ❌ 「Mastra 做不到动态计划」
> ❌ 「我们和 Mastra 零重叠」

### Q1：你这套动态计划，Mastra 的 Workflow 不是也能做吗？为什么不用？

**答**：不是"Mastra 做不到"，而是**一等抽象不同**。Mastra Workflow 的一等公民是**执行图（how to run）**——它擅长把"怎么跑"定义清楚、持久化、可观测；而我们的内核一等公民是**计划文档（what to do）**——一份可见、可编辑、可中断的计划数据。我们要解决的是"计划怎么长出来、怎么在失败时局部重排"，这是规划层的职责，不在 Mastra Workflow 的主场。

### Q2：那 Mastra 不支持运行时动态图吗？

**答**：恰恰相反，它支持。Mastra **Dynamic Workflows（≥1.58.0，PR #20471）** 可以把一份 JSON 图 POST 到运行中的 server 并持久化，重启仍在。所以"它是编译期静态的"这个说法是**错的**。但"图可以从运行时来"和"图该怎么长出来"是两件事——后者是 Plan 生成、依赖图求解、影响面闭包、收敛判定这些活，Dynamic Workflows 不解决。

### Q3：那你用 generic step 去模拟动态计划，走得通吗？

**答**：走得通，但等于把内核**在 Mastra 内部重写一遍**——图求解、局部子树重建、已完成步骤保留全塞进 generic step 的回调里。结果是不可移植（绑死 Mastra）、不可单测（依赖运行时）、不可跨领域复用。所以核心判断是**能做 ≠ 该做**。

### Q4：那你们的护城河到底是什么，跟 Mastra 没重叠？

**答**：有重叠，我不回避——执行/工具调用/记忆这些 Mastra 很强，我们后续就通过 `RuntimeAdapter` 接 `MastraRuntime` 复用它。**仍成立的是规划层护城河**：Plan 生成、依赖图求解、影响面闭包、收敛判定、Domain Pack 机制、局部子树重建 + 已完成步骤保留。Dynamic Workflows 解决"图可以从运行时来"，**不解决"图该怎么长出来"**。

### Q5：本期用了 Mastra 吗？

**答**：**M1 未引入 Mastra**，只用 `MockRuntime`，目标是零 API Key 跑通闭环、并先用 grep/git 证明内核与框架解耦。计划后续通过 `RuntimeAdapter` 接入 Mastra，内核一行不改——这正是 1.9 那条亮点的用意。

### Q6：如果重做，会直接上 Mastra 吗？

**答**：不会把规划逻辑塞进 Mastra，但会在 M2 把执行层换成 `MastraRuntime`，让真模型、真工具、记忆、评测直接用上 Mastra 的成熟能力，规划层保持自研。分工是：Mastra 管 how to run，我们管 what to do。

## 3. 高频追问与应答（★）

### Q1：为什么不直接用 LangGraph / Inngest / Temporal？

**答**：LangGraph 的一等公民也是执行图（节点+边+状态机），和 Mastra 同类问题——它能把计划画成图，但"计划作为可编辑文档、领域词零侵入内核"不是它的关注点，且 LangGraph 偏 Python/JS 双栈维护成本。Inngest / Temporal 是 durable execution，解决"长任务跨进程可恢复"，而本项目单轮 ≤25s、无长期后台任务，引入它们是过度工程，还会威胁 Cloudflare 镜像部署。我们的 RuntimeAdapter 抽象预留了接这些的能力，但 M1 不需要。

### Q2：和 ReAct / Plan-and-Execute 的区别？

**答**：ReAct 把"思考-行动"交替压在模型上下文，计划不可见、不可编辑。Plan-and-Execute 进了一步——先出计划再执行——但计划通常是一次性的、失败就整段重来。我们的差异在三点：(1) 计划是**可编辑文档**（L0/L1/L2 三档回写）；(2) 失败只重排**受影响子树**并保留已完成；(3) 重规划受**三重闸门 + 收敛判定**约束，不会无限循环。

### Q3：重规划不会无限循环吗？

**答**：三重闸门卡死上限：次数 ≤5、单轮成本 ≤¥2、单轮时长 ≤25s；再加收敛判定——重排结果与原受影响子树的 Jaccard delta < 0.15 判为原地打转，**强制转人工**（`NO_CONVERGENCE`）。闸门优先于收敛判定，二者任一拦截都停。代码里 `evaluateReplan` 一条路径走完。

### Q4：模型输出不可信怎么办？

**答**：三层：① 所有模型/网络 JSON 先 `safeParse`，失败降级 `RawPayloadCard`；② 内核只信 `ok`/`severity`，不读领域细节；③ 事实字段必须带 `SourceRef`，`producesFacts` 步骤无来源直接判失败（`SOURCE_MISSING`）。信任边界清晰：模型负责"生成结构"，数据源负责"提供事实"。

### Q5：为什么不用 Server Actions / RSC？

**答**：Server Actions 把服务端逻辑散落到组件里，破坏"服务端唯一入口是 `app/api/**`"的边界，也难做 SSE 流式与中断。RSC/`ai/rsc` 的 `streamUI` 官方标 experimental、不建议生产，且把组件渲染下沉到服务端，会夺走我"计划客户端可编辑"的自主权。所以全站 `'use client'`，流式走 Route Handler + SSE。

### Q6：前端流式为什么不用 `ai/rsc`？

**答**：同 1.7——`streamUI` 把生成式 UI 绑死在服务端 RSC，而我需要客户端对计划有完整编辑/续跑控制权；且它是 experimental。我选 SSE + JSON Patch 增量 + 16ms 合批，传输与渲染解耦，任何运行时都能接。

### Q7：这个 demo 有真实模型吗？怎么接？

**答**：M1 是 `MockRuntime`，连"模型"都是脚本化 fixture，**零 API Key 跑通闭环**——这是刻意的：先把架构与失败路径验证扎实。接真模型只需新增一个 `MastraRuntime` 实现 `RuntimeAdapter`（plan/replan/runTool 三个方法），内核零改；`plan()` 里现在 scripted 的部分换成真 LLM 调用即可。

### Q8：计划交给用户编辑，模型怎么配合？

**答**：编辑分三档：`L0` 只改未执行步骤文本，本地零成本改；`L1` 影响下游，从最早受影响的未完成步开始局部重排（保留已完成 id）；`L2` 改目标级约束，全量重排 `revision+1`。编辑命令只在终态（paused/failed/awaiting_user）生效，回传后服务端重新校验 plan 快照并归一状态——"先编辑、再原路重发"。

### Q9：成本怎么控制？

**答**：三重闸门里的成本闸门（≤¥2/轮）是硬上限；预算在 `RunContext.budgetRemainingCNY` 里随重规划递减，每轮重排 +¥0.05 计入；超出即停。另外 Mock 阶段成本恒为 0，所以成本控制逻辑现在是用脚本化故障注入验证的，真模型接入后会用真实 token 计费回填。

### Q10：如果让你重做，哪里会改？

**答**：① 真模型接入（M2，换 `MastraRuntime`）是最大的下一步；② 计划版本历史与 diff 视图（现在只有 revision 号，没有可视化对比）；③ 多领域路由现在是单域 demo，缺规则优先+模型兜底的路由层；④ 评测流水线（evaluation 段已留钩子但没 benchmark）。架构内核本身我基本不会动——因为 grep/git 已经证明它够干净、够通用。

### Q11：你测试覆盖够吗？纯函数都测了吗？

**答**：129 个测试用例全绿（`npm test` 退出 0）。所有纯函数（`PlanCompiler`/`cycleDetect`/`gates`/`impact`/`scheduler`/`edit`/`degrade`/`nodeReducer`）都有单测；闭环用 `closedLoop.test.ts` 端到端覆盖 normal / retry / 重规划保留已完成 / 澄清 / 中断 / 失败兜底 / 反幻觉。QA 背景让我特别在意：收敛判定踩过**两个方向**的坑（签名含 id → delta 恒 1.0 判定永不触发；比整个计划 → 只动一步被误判原地打转），两个反例都固化成了 `gates.test.ts` 的断言防回潮。

### Q12：持久化做了吗？断线后还能恢复吗？

**答**：M1 是单请求内闭环（≤25s），`paused` 状态在内存，没做长期持久化（PRD 明确 MVP 不做）。中断已经能正确转 `paused` 并下发 `done`，但因为没落库，刷新即丢失。这是已知取舍，不是疏漏——长期持久化在 P2 长任务异步化里。

## 5. 已知短板与诚实回答方式

**当前没做的（要主动、坦然地说，别等被问）**：

1. **没有真实模型**：M1 是 MockRuntime。→ "这是刻意的。我先证明架构和所有失败路径在零 Key 下都能跑通，再接真模型——这样真模型接入时只动 Runtime 实现，内核风险为零。"
2. **没有持久化**：`paused` 仅内存。→ "MVP 范围是单请求闭环（≤25s）。持久化是 P2 长任务异步化的事，架构上 `plan` 快照已可序列化、可直接落库，缺的只是存储层。"
3. **只有一个 demo 领域**：`src/domains/demo` 是验证装置不是真实业务域。→ "基座的卖点恰恰是'没领域也能跑、加领域不动内核'；demo 只是把闭环点燃的火柴。多领域正交验证是下一步。"
4. **没有评测 benchmark**：evaluation 段留了钩子但没数据。→ "反幻觉与收敛判定现在由单测和脚本化故障注入保证；真实 benchmark 需要真模型 + 真数据，和 M2 一起做。"

**把短板说成"有意识的取舍"而不是"没做完"的句式**：
- 先说边界（"MVP 范围是…"）
- 再说为什么现在不做（"因为会威胁 X / 超出单轮约束 / 属于下一里程碑"）
- 最后给证据"架构已经为它留好位置"（钩子/接口/可序列化快照）
